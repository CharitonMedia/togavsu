# Backup format TOGAVBK1

An archive is a tar file encrypted with AES-256-GCM. The passphrase is stretched with PBKDF2-HMAC-SHA256, 200000 iterations, a random 16-byte salt, and a random 4-byte nonce prefix. Each chunk is at most 1 MiB of plaintext. The chunk nonce is the prefix plus a big-endian counter. A wrong passphrase or a flipped ciphertext byte fails decryption.

On disk, under the backup volume:

- `{id}.tgbk` encrypted archive
- `{id}.sha256` hex digest of the encrypted bytes, checked before decrypt and after a destination copy
- `{id}.json` metadata: id, time, reason, checksum, size, destination errors

Plaintext dumps and extracted archives are written in a scratch directory outside that volume. Startup recovery and retention remove abandoned `staging-*` and `restore-*` directories on the volume and in that scratch directory. A workspace this process still has open is kept. Symlinks with those names are not followed. A missing destination directory before any upload is a completed failure. A timeout or a lost server response stays an uncertain receipt until the object is seen.

The id is `YYYYMMDDTHHMMSSZ-` plus 16 hex characters.

Each destination gets its own installation namespace (`namespace` on the destination record). New archives and their `.sha256` sidecars are written only under that directory or key prefix. On a path destination the two objects share the staged lifecycle in [path upload lifecycle](path-upload-lifecycle.md). A local receipt records the archive name after a successful copy. Retention deletes a receipt's archive and its sidecar together, and only after both deletes succeed. Files already in the configured root, including another firm's `.tgbk` names and checksums, are not adopted and are not deleted. A local delete keeps the metadata until every configured destination has removed that archive and its sidecar. Local retention still removes only the local volume and does not use that remote delete.

The tar contains:

- `manifest.json` with `format` `togavsu-backup-v1`, record counts, the dump checksum, and logical file names
- `db/dump.sql` plain `pg_dump` output
- `files/bytes.tar` the core's file export (`file_bytes` in the manifest: name, SHA-256, size). The supervisor reads it from the core's `GET /internal/v1/file-bytes` with its token while the core runs. It is the files service's `ExportBytes` stream: `files-manifest.json` (object id, kind, file, storage backend, key, size, SHA-256), then `objects/{id}` with the verified plaintext of each file version and rendition, Markdown copies included, from every storage backend with backups on. Each immutable version or rendition is copied once per archive. The core sends a `X-Togavsu-Export: complete` trailer after the last byte; a stream without it, a redirect, or a body that is not `application/x-tar` fails the backup. The safety backup a restore takes while the core is stopped has no `file_bytes`; the restore never deletes stored file bytes, so that rollback point still has them.
- `files/{sha256}` legacy content-addressed blobs (`files` in the manifest). No current writer produces them.

An archive uploaded for a restore or fetched from a destination is written as `{id}.tgbk` under the same publication intent. Its sidecar and `.json` record (with `source`) are published only after the received bytes match the supplied `.sha256` sidecar and the archive decrypts and passes the manifest checks below; otherwise the intent removes it. An existing id is never overwritten.

Restore rejects paths that escape the staging directory, rejects non-regular files, and refuses the dump when its checksum does not match the manifest. A manifest that lists legacy `files` blobs, or a `file_bytes` export when no core file import is wired, is rejected before writers stop and before the database is replaced. A `file_bytes` export whose size or SHA-256 differs from the manifest is refused at decrypt, before writers stop. After the database is replaced and the core is restarted, the supervisor sends `files/bytes.tar` to the core's `PUT /internal/v1/file-bytes` (retrying while the core is still starting, up to three minutes). The core's `RestoreBytes` writes each object to the backend and key the restored database names, with that location's encryption, and checks its SHA-256 there against the `file_versions` or `file_renditions` row; an object that already reads back correctly is left alone, and a file purged from the trash stays purged. If that step fails the restore record is `failed` with error `files_not_restored`: the restored database is live and the admin is mailed. Module data volumes are not in the archive.

The core fronts these routes at `/api/v1/backups`, `/api/v1/backup-destinations`, `/api/v1/backup-uploads` and `/api/v1/restores` (admin role, `backups:admin` scope for tokens and `/mcp`, each write in the audit log). A restore needs the installation's backup passphrase. An uploaded archive is kept on the core volume until a restore takes it. One the supervisor already holds with the same SHA-256 (downloaded from this installation) is restored by its own id. Any other is sent, with its computed `.sha256` sidecar, to `POST /v1/restores/upload` under the `backup_id` it was uploaded with (its file name), because the manifest inside names that id; without one the restore is refused. The core writes the `backups.passphrase` setting to `BACKUP_PASSPHRASE_FILE` once setup is complete and before each backup or restore it asks for. The monthly test-restore loads the dump into `togavsu_check_<hex>` on the admin database and compares those counts with the manifest. Only a mismatch is queued for admin mail.
